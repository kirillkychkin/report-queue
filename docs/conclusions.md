# Выводы: когда применять, преимущества, ограничения

## 1. Когда вообще нужна очередь задач

Очередь задач нужна, когда выполняется хотя бы одно:

- работа длится дольше, чем пользователь готов ждать ответ HTTP (секунды и больше);
- работа может упасть по внешней причине и её нужно **повторить** (почта, платёжный шлюз, внешний API);
- нагрузка приходит пиками, а обрабатывать можно равномерно — очередь = **буфер**;
- обработку нужно **масштабировать отдельно** от веб-слоя (CPU-задачи, генерация файлов, ML-инференс);
- нужны **периодические** задания (beat / scheduler) без cron на каждом сервере.

Очередь **не нужна**, если задача занимает десятки миллисекунд и её потеря при рестарте допустима —
достаточно `BackgroundTasks` FastAPI или `asyncio.create_task`. Она **не подходит** как RPC с ответом за миллисекунды
и как гарантия порядка событий (для этого — Kafka/партиции).

## 2. Celery

**Применять**, когда: несколько типов задач с разным приоритетом (маршрутизация по очередям), нужны пайплайны
(chain/group/chord), периодические задачи (beat), выбор брокера (RabbitMQ для гарантий, Redis для простоты),
мониторинг (Flower), rate limiting, лимиты времени, разные пулы (prefork/threads/gevent).

**Преимущества**

- Богатая модель надёжности: `acks_late`, `reject_on_worker_lost`, `autoretry_for` + `retry_backoff` + jitter, `time_limit`.
- Canvas — декларативные пайплайны без ручного связывания задач.
- Долгоживущий пул процессов: накладные расходы на задачу — ≈3 мс end-to-end (эксперимент, `noop`, пустая очередь).
- Брокер заменяется конфигурацией: одно и то же приложение работало на Redis и RabbitMQ без изменений в коде задач.

**Ограничения**

- Сложность: десятки настроек, неочевидные умолчания (`acks_early`, `prefetch_multiplier=4`, `visibility_timeout` на Redis).
- Синхронная модель: в asyncio-приложении `delay()` блокирует, `await` результата нет.
- `PENDING` означает «неизвестно»: result backend не хранит незапущенные задачи — нужен свой реестр заказов.
- На Windows prefork не работает надёжно (только `solo`/`threads`) — разработка и запуск через Docker.
- Result backend обязателен отдельно (RabbitMQ его не даёт) — на практике Redis нужен всегда.

## 3. RQ

**Применять**, когда: уже есть Redis, задач немного и они «крупные» (секунды), команда хочет прочитать весь код фреймворка,
нужна изоляция задач друг от друга (fork) — например, ненадёжный сторонний код с утечками памяти.

**Преимущества**

- Минимализм: задача — функция, очередь — имя + соединение; вся модель понятна за час.
- Явные статусы `queued / started / deferred / scheduled / finished / failed` и `Job.fetch` — API может честно ответить 404.
- `Retry`, `depends_on`, встроенный scheduler, `job.meta` для прогресса, failed-registry для разбора ошибок.
- Fork на каждую задачу: падение или утечка в задаче не убивает воркер и не влияет на следующие задачи.

**Ограничения**

- Только Redis — нет RabbitMQ-гарантий (publisher confirms, DLX).
- Fork на каждую задачу стоит ≈75 мс (Docker Desktop/WSL2) — на микрозадачах RQ `Worker` в 20+ раз медленнее Celery
  (13 против 300 задач/с на воркер), на 60-мс задачах — в 2,5 раза; `SimpleWorker` убирает эту цену вместе с изоляцией и уравнивает RQ с Celery.
- Нет canvas: chord/group собираются вручную через `depends_on`; результат зависимости читается явно.
- Не работает на Windows (fork); отложенные повторы требуют scheduler в воркере (`with_scheduler=True`).
- Несколько обращений к Redis на постановку одной задачи — но в эксперименте постановка всё равно быстрее, чем у Celery
  (2100–2400 против 900–1650 msg/s): протокол kombu дороже, чем два простых Redis-вызова.

## 4. Redis как брокер

**Применять**: dev/демо, небольшие и средние нагрузки, когда Redis уже есть (кэш, сессии) и потеря редкого сообщения при
аварии допустима или компенсируется идемпотентностью + повтором с уровня приложения.

**Преимущества**: одна зависимость на всё (брокер + result backend + очередь RQ), минимальная задержка, простота эксплуатации.

**Ограничения**: нет настоящего ack — Celery эмулирует его через `visibility_timeout` (задача дольше часа будет доставлена
повторно); персистентность RDB/AOF допускает потерю последних записей при падении; нет маршрутизации exchange/binding,
приоритеты эмулируются несколькими списками; нет DLX «из коробки».

## 5. RabbitMQ как брокер

**Применять**: продакшен с требованием «не потерять ни одной задачи», сложная маршрутизация (topic/fanout), несколько
потребителей на одно событие, dead-letter очереди, ограничение prefetch на уровне брокера, наблюдаемость через Management UI.

**Преимущества**: настоящие ack/nack/reject, durable-очереди + persistent-сообщения, publisher confirms, DLX, TTL,
per-consumer prefetch, зрелые инструменты.

**Ограничения**: отдельный сервис (Erlang VM, память под очереди), нет result backend, сложнее модель (exchange → binding → queue).

**Про скорость — аккуратно.** В эксперименте Celery на RabbitMQ оказался в 1,5–1,8 раза быстрее, чем на Redis, на микрозадачах,
но это не «RabbitMQ быстрее Redis»: публикация в AMQP по умолчанию не ждёт подтверждения, а каждая команда Redis ждёт ответа
(≈110 мкс round-trip). Включите publisher confirms — и постановка в RabbitMQ падает до 218 msg/s, в 8 раз медленнее Redis
(замер: `bench/diagnose.py`). На реальных задачах (≥ 50 мс) оба транспорта неразличимы. Итог: **выбирать RabbitMQ надо
за гарантии и маршрутизацию, а не за скорость** — за настоящие гарантии на публикации придётся заплатить пропускной способностью.

## 6. Чеклист выбора

| Вопрос | Да → |
|---|---|
| Задачи короткие (< 50 мс) и их тысячи в секунду? | Celery (prefork/threads) или RQ `SimpleWorker`; **не** RQ `Worker` |
| Нужны пайплайны, периодика, приоритеты, разные пулы? | Celery |
| Уже есть Redis, задач немного, важна простота? | RQ |
| Потеря задачи недопустима? | RabbitMQ + `acks_late` + идемпотентность + DLX |
| Приложение на asyncio? | arq / Taskiq / Dramatiq(asyncio) — или Celery через thread executor |
| Нужен порядок событий и replay истории? | Kafka / Redis Streams — это не очередь задач |
| Сложные долгие бизнес-процессы с компенсациями? | Temporal / Prefect (workflow-движки) |
| Задача занимает < 10 мс и может потеряться при рестарте? | `BackgroundTasks` / `asyncio.create_task` — без брокера |

## 7. Главные уроки проекта

1. **Идемпотентность — не опция.** При at-least-once (`acks_late`) повтор задачи неизбежен; `report_id` + `seed` делают его безопасным.
2. **Абстракция над фреймворком дёшева и полезна**, пока не нужны его уникальные фичи; она же позволила провести честное сравнение.
3. **Умолчания фреймворков — архитектурные решения.** `acks_early` и `prefetch=4` в Celery, fork в RQ, `visibility_timeout` в Redis
   меняют гарантии и производительность в разы — их нужно выбирать осознанно.
4. **Брокер — не хранилище.** Маленькие сообщения, результаты — в result backend/файлах, TTL на всё.
5. **Измерять, а не верить — но и мерить надо то, что думаешь.** Разница между RQ `Worker` и `SimpleWorker` — в 20 раз.
   Разница между Redis и RabbitMQ под Celery (1,5× на пустых задачах, 0 % на реальных) оказалась не свойством брокеров,
   а свойством конфигурации: у AMQP публикация не подтверждается, а у Redis-транспорта каждая операция — синхронный
   round-trip, и в замере один Redis обслуживал и брокер, и события Flower, и результаты (26 команд на задачу против 13).
   Сам Redis при этом работал на 10 % своего потолка. Разбор — в `docs/experiment.md`, раздел «Аудит».
6. **От 50 мс полезной работы фреймворк и брокер перестают влиять на пропускную способность** — выбирать надо по гарантиям,
   удобству и эксплуатации, а масштабировать — воркерами (ускорение ×3,4–4,1 на 4 воркерах).
