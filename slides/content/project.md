## Задача и домен
> Заказ отчёта, который нельзя сделать внутри HTTP-запроса

- **Домен**: генерация отчёта по продажам — синтетические данные (pandas) → агрегация по периоду / региону / категории → три артефакта: `summary.csv`, `chart.png` (matplotlib), `report.pdf`.
- **Почему домен именно такой**: работа реально нагружает CPU (0,4–3 с на 10 000–200 000 строк), даёт файлы на выходе и прогресс по шагам — то, ради чего очередь и нужна.
- **Сценарий**: `POST /reports` → `202 {id}` → генерация в воркере → `GET /reports/{id}` (статус + прогресс) → `GET /reports/{id}/download?format=csv|png|pdf`.
- **Что специально не делал**: базу данных, авторизацию, вебсокеты — они не относятся к теме и раздули бы демо.

!> Одна и та же доменная функция `generate_report()` выполняется четырьмя способами: Celery+Redis, Celery+RabbitMQ, RQ, и вообще без фреймворка (голый pika).

::: notes
Начать с того, что демо не «игрушечное»: задача действительно долгая, действительно пишет файлы и действительно требует прогресса.

## Архитектура и стек
> Три слоя, ни один не знает о соседях больше необходимого

| Слой | Пакет | Знает о | Не знает о |
|---|---|---|---|
| Домен | `app/reports` | pandas, matplotlib, файлы | очередях, Celery, RQ, HTTP |
| Адаптеры задач | `app/tasks` | Celery, RQ, pika, брокерах | HTTP |
| API и UI | `app/api` | HTTP, протокол `TaskBackend` | какой фреймворк внизу |

- **Стек**: FastAPI + uvicorn, Celery 5.6 (+ Flower, beat), RQ 2.12, Redis 7, RabbitMQ 3.13, pandas 3.0 + matplotlib (backend Agg), pydantic-settings.
- **Инфраструктура**: `docker compose up --build` поднимает redis, rabbitmq, api (`:8000`), worker-celery, worker-rq, beat, flower (`:5555`). Один образ на все сервисы приложения.
- **Артефакты** — на общем volume, в result backend только имена файлов: сообщение и результат остаются маленькими.

::: notes
Подчеркнуть: воркеры только в Docker — RQ использует fork (нет на Windows), Celery prefork на Windows нестабилен. Это зафиксированное архитектурное ограничение, а не лень.

## Ключевые решения
> Каждое — с ценой, которую я готов назвать

| Решение | Почему | Цена / где не работает |
|---|---|---|
| Абстракция `TaskBackend` | API не зависит от фреймворка → честное сравнение и замена | canvas и `depends_on` доступны только внутри адаптеров |
| `task_id = report_id` | статус по своему id без таблицы «заказ → задача», идемпотентность | Celery не отличает «нет заказа» от «в очереди» (оба `PENDING`) |
| `acks_late=True`, `prefetch=1` | падение воркера не теряет заказ, честное распределение | at-least-once → нужна идемпотентность; медленнее на микрозадачах |
| Очереди `reports` / `notifications` | CPU-задачи не задерживают быстрые уведомления | больше воркеров и конфигурации |
| Результат — файлы, не payload | брокер — транспорт, а не хранилище | нужен общий volume, в кластере — S3 |
| Только JSON-сериализация | `pickle` = выполнение произвольного кода при доступе к брокеру | аргументы только простых типов |

```python
class TaskBackend(Protocol):
    def enqueue_report(self, report_id: str, params: ReportParams) -> str: ...
    def get_status(self, report_id: str) -> ReportStatus: ...
```

::: notes
Если спросят «зачем абстракция, это же оверинжиниринг»: без неё сравнение Celery и RQ было бы сравнением двух разных приложений, а не двух очередей.

## Что покажу за 5 минут
> Сценарий демонстрации (`docs/demo.md`)

- **Старт**: `docker compose up -d --build` → `docker compose ps` (7 сервисов), `GET /health` — пинг брокера.
- **Заказ отчёта** в UI (`http://localhost:8000`): параметры → `202 {id}` → прогресс 20 → 100 % через polling → скачивание CSV / PNG / PDF.
- **Распределённая обработка**: `docker compose up -d --scale worker-celery=3`, пакет из 9 отчётов — во Flower видно, как задачи расходятся по трём воркерам.
- **Надёжность**: `NOTIFY_FAILURE_RATE=0.7` — в логах видны повторы с экспоненциальным backoff; убитый воркер (`docker kill`) не теряет задачу — она уходит другому (`acks_late`).
- **Смена фреймворка**: `TASK_BACKEND=rq` в `.env` → `docker compose up -d api` → тот же UI, тот же результат, другой исполнитель.
- **Под капотом**: `python -m app.tasks.raw_amqp produce 6` / `consume` — producer/consumer на голом pika, durable-очередь, ручной `basic_ack`, DLX.

::: notes
Порядок важен: сначала «работает», потом «масштабируется», потом «не теряет», и только в конце — «а вот как это устроено без фреймворка».

## Результаты и что из них следует
> N = 1000, медиана трёх повторов

| Конфигурация | noop 1w → 4w | cpu_small 1w → 4w | Постановка, msg/s |
|---|---|---|---|
| Celery + Redis | 302 → 739 | 17 → 63 | ≈900 |
| Celery + RabbitMQ | **474 → 1336** | 19 → 67 | ≈1600 |
| RQ `Worker` (fork) | 13 → 44 | 7 → 23 | 2100–2400 |
| RQ `SimpleWorker` | 300 → 846 | 19 → 64 | 2100–2400 |

- Накладные расходы очереди — **≈3 мс** на задачу end-to-end (Celery + Redis, 4 воркера: p50 = 3 мс, p99 = 4 мс).
- **От ≈50 мс полезной работы фреймворк и брокер не влияют** на пропускную способность — выбирать надо по гарантиям, а не по бенчмаркам.
- Масштабирование воркерами — **×3,4–4,1** при четырёх воркерах; `fork` в RQ стоит порядок величины на микрозадачах.
- **Проверил контринтуитивный результат** (RabbitMQ быстрее Redis): это не про брокеры — AMQP не подтверждает публикацию, а в конфигурации с Redis один сервер обслуживал брокер, события и результаты (26 команд на задачу против 13). С `confirm_publish=True` RabbitMQ в 8 раз медленнее Redis. Разбор — `docs/experiment.md`, «Аудит».

::: notes
Главное методическое решение: timestamps пишет сама задача в общий Redis-список, поэтому метрики одинаковы для всех фреймворков и не зависят от их result backend.

## Ограничения проекта
> Где это демо честно не работает

- **Нет реестра заказов**: при `TASK_BACKEND=celery` неизвестный `report_id` отдаёт `PENDING`, а не 404 — сознательно оставлено, чтобы показать различие Celery и RQ.
- **Polling вместо push**: лишние запросы; в продакшене — SSE или webhook.
- **Общий volume вместо объектного хранилища**: на нескольких хостах нужен S3/MinIO.
- **Нет транзакционного outbox**: «записать в БД и поставить задачу» здесь не атомарно (БД в демо нет вовсе).
- **Бенчмарк на одном хосте** под Docker Desktop/WSL2: показывает порядки величин и характер масштабирования, а не пределы брокеров.
- **Celery синхронный** внутри асинхронного FastAPI: постановка задачи блокирует event loop на доли миллисекунды — при больших объёмах нужен arq/Taskiq или executor.

::: notes
Этот слайд — заготовка под вопрос «а что бы вы поменяли для продакшена»: реестр заказов в БД, S3, SSE, outbox.

## Выводы
> Что я понял, пока делал проект

- **Идемпотентность — условие корректности**, а не оптимизация: при `acks_late` повтор задачи гарантированно случится.
- **Умолчания фреймворков — это архитектурные решения**: `acks_early` и `prefetch=4` в Celery, fork в RQ, `visibility_timeout` в Redis меняют гарантии и скорость в разы.
- **Абстракция над фреймворком дёшева** и окупается ровно до того момента, когда нужны его уникальные возможности.
- **Измерять, а не верить**: RQ `Worker` против `SimpleWorker` — 20×; Redis против RabbitMQ на реальных задачах — 0 %.
- **Брокер — транспорт, а не хранилище**: маленькие сообщения, результаты в файлах, TTL на всё.
