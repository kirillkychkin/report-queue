# Эксперимент: Celery vs RQ, Redis vs RabbitMQ

## Вопросы

1. Сколько «стоит» сама очередь — накладные расходы на постановку и на проход одной задачи?
2. Как меняется картина при CPU-задаче и при IO-ожидании?
3. Насколько линейно масштабируется пропускная способность при добавлении воркеров?
4. Отличается ли Celery на Redis от Celery на RabbitMQ при одинаковом коде задач — и при одинаковых гарантиях?
5. Что даёт модель «процесс на задачу» в RQ и сколько она стоит?

Матрица прогонялась дважды. Первая версия дала контринтуитивный результат («RabbitMQ быстрее Redis»),
аудит нашёл в методике три перекоса, они исправлены, и матрица переснята. Ниже — результаты **исправленной**
методики (v2); разбор ошибок v1 и сравнение цифр — в разделе «Что было не так в первой версии».

## Методика

### Конфигурации

| Конфигурация | Фреймворк | Брокер | Модель воркера / особенность |
|---|---|---|---|
| `celery-redis` | Celery 5.6.3 | Redis 7 | prefork, `--concurrency=1`, `acks_late`, `prefetch_multiplier=1` |
| `celery-rabbitmq` | Celery 5.6.3 | RabbitMQ 3.13 | то же; publish по умолчанию — без подтверждения |
| `celery-rabbitmq-confirm` | Celery 5.6.3 | RabbitMQ 3.13 | то же + **publisher confirms** — сравнение при равных с Redis гарантиях публикации |
| `rq-redis` | RQ 2.12.0 | Redis 7 | `Worker` — **fork на каждую задачу** (умолчание RQ) |
| `rq-simple-redis` | RQ 2.12.0 | Redis 7 | `SimpleWorker` — задача в процессе воркера (аналог Celery `--pool=solo`) |

Общее для всех: одна и та же полезная нагрузка (`bench/tasks.py`), один и тот же сборщик метрик,
события Celery для Flower **выключены** (`CELERY_EVENTS=false`), result backend и метрики — на отдельном
Redis (`redis-backend`), чтобы брокер не делил сервер с хранилищем.

### Виды задач

- `noop` — ничего не делает: чистые накладные расходы очереди (сериализация, брокер, ack, запись результата);
- `cpu_small` — pandas-агрегация 10 000 строк + один график matplotlib (≈46 мс CPU);
- `io_sleep` — `time.sleep(0.05)`: имитация сетевого ожидания.

### Три фазы одного прогона

Ключевое отличие от v1: три разные величины измеряются отдельно, а не одним числом.

1. **Постановка.** Потребление останавливается (Celery — `cancel_consumer`, RQ — задачи копятся в отдельном
   списке `rq:queue:bench_hold`), затем N задач публикуются в пустую очередь. Получается чистая цена публикации,
   без конкуренции с воркерами.
2. **Разбор очереди.** Потребление возвращается (Celery — `add_consumer`, RQ — атомарный `RENAME` списка:
   очередь RQ — обычный список Redis, а `RENAME` будит клиентов, заблокированных на `BLPOP`). Очередь заведомо
   полна, воркеры не простаивают. Пропускная способность считается по timestamp'ам самих задач:
   `N / (последний finish − первый start)`.
3. **Задержка.** M = 30 задач по одной, с ожиданием каждой, на **пустой** очереди. Это настоящие накладные
   расходы на задачу, а не время ожидания в очереди.

- **Нагрузка**: `noop` — N = 5000, `cpu_small`/`io_sleep` — N = 1000; воркеров 1, 2, 4 (отдельные контейнеры,
  `docker compose --scale`). Для `rq-redis` (fork ≈ 70 мс/задача) N меньше — 1000/500/500: пропускная способность
  и задержка это скорости, от N они не зависят, а прогон иначе растягивается в разы.
- **Продьюсер** живёт в отдельном контейнере (`api`), а не внутри воркера.
- **Тишина вокруг**: на время матрицы гасятся `beat` (иначе каждые 10 минут публикует `cleanup` в ту же
  очередь `reports`) и `flower`.
- **Повторы**: 3 на ячейку, берётся медиана. Перед каждым прогоном очередь очищается и проверяется число живых воркеров.
- **Оркестрация**: `bench/run_matrix.py` (хост) → `docker compose … --scale` → `bench/runner.py` (контейнер `api`) →
  `results/raw.csv` → `results/summary.csv` (медианы) → `bench/plot.py` → графики и `results/summary.md`.

### Окружение

- Хост: Intel Core i7-11700F (8 ядер / 16 потоков), 32 ГБ RAM, Windows 11, Docker Desktop 28.0.4 (WSL2, Ubuntu),
  контейнерам доступно 16 CPU и 15.6 ГиБ.
- Образы: `python:3.12-slim`, `redis:7-alpine` (`appendonly yes`) ×2 (брокер и backend), `rabbitmq:3.13-management-alpine`.
- Все контейнеры — на одном хосте; часы общие, поэтому timestamps сравнимы. RTT между контейнерами ≈ 100 мкс
  (замер `bench/diagnose.py`) — в продакшене с брокером на другой машине абсолютные цифры будут хуже, соотношения — похожими.
- Прогон: 135 конфигураций-повторов, 89 минут, 0 сбоев.

## Результаты

Полные данные: `bench/results/raw.csv` (135 прогонов), медианы — `results/summary.csv`, таблицы — `results/summary.md`.
Данные первой версии сохранены в `bench/results/v1/`.

### Пропускная способность (разбор заранее наполненной очереди)

![throughput](../bench/results/throughput.png)

| Наблюдение | Цифры (1 воркер → 4 воркера) |
|---|---|
| **На «настоящих» задачах брокер и фреймворк не важны.** При 46 мс CPU или 50 мс IO все конфигурации без fork дают одно и то же | cpu_small: 19–20 → 65–68; io_sleep: 16–17 → 64–69 |
| **На микрозадачах RabbitMQ как транспорт Celery быстрее Redis в 1,2–1,3 раза.** Разрыв сокращается с ростом числа воркеров | noop: 560 → 1744 против 434 → 1497 |
| **Publisher confirms не влияют на разбор очереди** — они цена только для публикующей стороны | noop: 554 → 1649 против 560 → 1744 |
| **Fork на задачу стоит порядок величины** на микрозадачах и ≈2,8× на реальных | noop: 13 → 45; cpu_small: 7 → 24 |
| **RQ `SimpleWorker` уступает Celery на микрозадачах** (в v1 они выглядели одинаково) | noop: 296 → 939 против 434 → 1497 |

### Масштабирование

![scaling](../bench/results/scaling.png)

- Ускорение на 4 воркерах: `noop` ×3,0–3,5, `cpu_small` ×3,4–3,5, `io_sleep` ×3,8–4,1 — близко к линейному везде.
- В v1 у `noop` было «×2,4 у Celery+Redis», и это был артефакт: очередь пустовала, и упирались в продьюсера.
  На заранее наполненной очереди тот же Celery+Redis даёт **×3,45**.
- Брокер начинает отставать от идеала только на пустых задачах и четырёх воркерах — то есть при ≥1500 задачах/с.

### Накладные расходы на одну задачу (пустая очередь)

![latency](../bench/results/latency.png)

| Конфигурация | p50 | p95 | Что это значит |
|---|---:|---:|---|
| Celery + Redis | 1,8 мс | 2,4 мс | сериализация → брокер → воркер → результат |
| Celery + RabbitMQ | 1,8 мс | 2,3 мс | транспорт на задержку одной задачи не влияет |
| Celery + RabbitMQ (confirms) | 1,8 мс | 2,3 мс | на пустом брокере подтверждение приходит сразу |
| RQ (SimpleWorker) | 3,5 мс | 4,3 мс | RQ делает больше обращений к Redis на задачу |
| RQ (fork) | 72,1 мс | 80,2 мс | **цена `fork()`** в Docker Desktop/WSL2 |

- Для `cpu_small` задержка 48–51 мс при 46 мс полезной работы, для `io_sleep` — 54–59 мс при 50 мс:
  накладные расходы очереди тонут в работе уже на задачах в десятки миллисекунд.
- Fork у RQ добавляет к каждой задаче те же ≈70 мс (cpu_small: 140 мс против 51 мс у SimpleWorker).

### Скорость постановки

![enqueue](../bench/results/enqueue.png)

| Конфигурация | msg/s | Почему так |
|---|---:|---|
| RQ (SimpleWorker / fork) | 2567 / 2366 | простое сообщение, 2–3 команды Redis, никакого AMQP-протокола |
| Celery + RabbitMQ | 2333 | `basic_publish` не ждёт ответа брокера |
| Celery + Redis | 1583 | каждая команда Redis ждёт ответа (RTT ≈ 110 мкс) |
| **Celery + RabbitMQ (confirms)** | **210** | publish ждёт подтверждения; для persistent-сообщений это ожидание сброса на диск |

Главное здесь: **преимущество RabbitMQ на постановке существует только до тех пор, пока публикация
не подтверждается**. Включаем publisher confirms — и постановка становится в 7,5 раза медленнее Redis,
хотя на разбор очереди это не влияет вовсе (554 против 560 задач/с). При этом задержка одиночной
публикации не страдает (1,8 мс) — похоже, дело в батчинге сброса на диск: в потоке публикаций каждое
подтверждение ждёт своей группы, на пустом брокере — не ждёт.

## Ответы на вопросы

1. **Сколько стоит очередь?** 1,8 мс на задачу end-to-end у Celery (оба брокера), 3,5 мс у RQ `SimpleWorker`,
   72 мс у RQ `Worker` (fork). Постановка: 1,6–2,6 тыс. сообщений/с, кроме RabbitMQ с confirms — 210.
2. **CPU и IO задачи?** От ≈50 мс полезной работы накладные расходы очереди неразличимы (< 5 %) — выбирать
   надо по гарантиям и удобству, а не по скорости.
3. **Масштабирование?** Близко к линейному до 4 воркеров на всех видах задач (×3,0–4,1).
4. **Redis vs RabbitMQ под Celery?** На микрозадачах RabbitMQ быстрее в 1,2–1,3 раза по разбору очереди
   и в 1,5 раза по постановке — но только без подтверждения публикации. С confirms он в 7,5 раза медленнее
   Redis на постановке. На реальных задачах разницы нет. Вывод: **брокер выбирается по гарантиям и маршрутизации,
   а не по скорости**.
5. **Fork в RQ?** ≈70 мс на задачу: на микрозадачах это в 23 раза медленнее `SimpleWorker`, на 46-мс задачах — в 2,8 раза.

## Что было не так в первой версии

Первая матрица дала «RabbitMQ быстрее Redis в 1,5–1,8 раза» — результат, противоречащий интуиции
(Redis — быстрый in-memory сервер). Проверка данных показала, что сам замер воспроизводим (135/135 прогонов
с нужным числом воркеров, медианный разброс повторов 1,02×), а вот сравнивались **не те объекты**. Диагностика —
`bench/diagnose.py` (`docker compose exec -T api python -m bench.diagnose publish`):

| Замер из контейнера | Результат |
|---|---|
| Redis `PING` / `LPUSH` по одной | 10 347 / 9 056 оп/с (RTT ≈110 мкс) |
| Redis `LPUSH` пачками по 100 | 106 725 оп/с |
| Celery: публикация → Redis | 1 169 оп/с (855 мкс) |
| Celery: публикация → Redis, без событий Flower | 1 745 оп/с (573 мкс) |
| Celery: публикация → RabbitMQ | 1 901 оп/с (526 мкс) |
| Celery: публикация → RabbitMQ + confirms | 218 оп/с (4 584 мкс) |

Redis работал на ~10 % своего потолка — упирались не в него, а в число синхронных round-trip'ов.
Плюс три перекоса в самой методике:

| Дефект v1 | Почему это искажало результат | Исправление в v2 |
|---|---|---|
| Один Redis обслуживал брокер, шину событий Flower, result backend и метрики бенчмарка — **26 команд на задачу** против 13 у конфигурации с RabbitMQ | «Celery + Redis» получал вдвое больше работы на одном однопоточном сервере, а у «Celery + RabbitMQ» половина уезжала на другой сервер | отдельный `redis-backend` под результаты и метрики; `CELERY_EVENTS=false` |
| Пропускная способность считалась от первой постановки до последнего завершения при живых воркерах | На микрозадачах очередь пустовала → измерялась скорость продьюсера, а не воркеров (отсюда «×2,4» в масштабировании) | очередь наполняется при остановленном потреблении, затем измеряется разбор |
| «Задержка» = время от постановки до завершения при N задачах в очереди | Это закон Литтла (позиция в очереди), а не цена задачи; «≈3 мс» были выхвачены из единственной ячейки, где очередь случайно оказалась пустой | отдельная фаза: 30 задач по одной на пустой очереди |
| Продьюсер работал внутри контейнера воркера | конкуренция за CPU | продьюсер в контейнере `api` |
| `beat` публиковал `cleanup` в ту же очередь каждые 10 минут, `flower` держал соединение | посторонние задачи и трафик во время замеров | оба сервиса гасятся на время матрицы |
| Сравнивались конфигурации с разными гарантиями публикации | AMQP не подтверждает publish, Redis отвечает на каждую команду | добавлена конфигурация `celery-rabbitmq-confirm` |

Как изменились цифры (noop, 1 воркер):

| Метрика | v1 | v2 | Причина изменения |
|---|---:|---:|---|
| Celery + Redis, задач/с | 302 | **434** | убраны события и лишняя нагрузка на Redis; измеряется разбор, а не продьюсер |
| Celery + RabbitMQ, задач/с | 474 | **560** | то же |
| Отношение RabbitMQ / Redis | 1,57× | **1,29×** | исчезла асимметрия нагрузки |
| Постановка, Redis / RabbitMQ | 989 / 1645 | **1583 / 2333** | нет событий и конкуренции с воркером |
| Масштабирование Celery + Redis (noop, 1→4) | ×2,4 | **×3,45** | в v1 упирались в продьюсера |
| Накладные расходы на задачу | «≈3 мс» (одна ячейка) | **1,8 мс** (30 замеров) | прямой замер на пустой очереди |
| Цена `fork` в RQ | «≈75 мс» (оценка из throughput) | **72,1 мс** (прямой замер) | прямой замер |

Выводы v1, которые **устояли**: fork в RQ стоит порядок величины; от ≈50 мс работы брокер и фреймворк
перестают влиять; масштабирование близко к линейному; идемпотентность обязательна при `acks_late`.
Вывод, который **пришлось переформулировать**: «RabbitMQ быстрее Redis» → «Redis-транспорт kombu платит
round-trip за каждую операцию, а AMQP по умолчанию не подтверждает публикацию; при равных гарантиях
Redis на постановке в 7,5 раза быстрее».

## Оговорки

- Один хост: брокеры, воркеры и продьюсер конкурируют за одни ядра; при 4 воркерах `cpu_small` это уже заметно.
- Docker Desktop на Windows = виртуальная машина WSL2: `fork` и файловые операции дороже, чем на «голом» Linux;
  RTT до брокера ≈110 мкс — на выделенной сети было бы меньше, и разрыв между транспортами сократился бы.
- Продьюсер один и однопоточный: цифры постановки — это стоимость одного сообщения, а не предел брокера.
  Оба фреймворка умеют батчить (`enqueue_many`, переиспользование producer), здесь намеренно «наивная» постановка.
- События Celery выключены ради честного сравнения, но в реальной эксплуатации Flower обычно включён —
  это минус ≈15 % к постановке на Redis (1745 → 1169 оп/с по диагностике).
- Разбор очереди измеряется на заполненной очереди — это верхняя граница пропускной способности;
  в проде очередь обычно не забита, и тогда важнее задержка, а не throughput.
- N = 500–5000 — микро-нагрузка: показывает порядок величин и характер масштабирования, а не пределы брокеров.
- `cpu_small` использует pandas и matplotlib, которые сами по себе многопоточны в мелочах;
  при 4 воркерах на 16 потоках это не упирается в CPU, но на слабой машине результат будет другим.
