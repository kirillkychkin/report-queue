# Термины и определения

> Шпаргалка к докладу «Очереди сообщений и фоновые задачи в Python». Термины сгруппированы по темам,
> внутри группы — в порядке появления в докладе. Курсивом дан английский оригинал.

## 1. Базовые понятия

**Очередь сообщений** (*message queue*) — механизм передачи данных между процессами, при котором отправитель кладёт сообщение в промежуточное хранилище, а получатель забирает его позже. Отправитель и получатель разделены во времени: получателя может не быть в момент отправки.

**Брокер сообщений** (*message broker*) — сервис, который принимает, хранит и раздаёт сообщения (Redis, RabbitMQ, Kafka). Отвечает за доставку, но не за бизнес-логику.

**Продьюсер** (*producer, publisher*) — сторона, которая публикует сообщение. В проекте это API: приняв HTTP-запрос, он ставит задачу и сразу отвечает клиенту.

**Консьюмер** (*consumer, subscriber*) — сторона, которая забирает сообщение и обрабатывает его.

**Воркер** (*worker*) — процесс-исполнитель фоновых задач: подключается к брокеру, забирает задачи, выполняет, подтверждает. Масштабирование = запуск дополнительных воркеров.

**Фоновая (асинхронная) задача** (*background task*) — единица работы, выполняемая вне цикла «запрос — ответ»: генерация файла, рассылка, обращение к внешнему API.

**Очередь задач** (*work queue, task queue*) — модель, в которой одно сообщение получает **ровно один** обработчик. Служит для распределения нагрузки.

**Publish/Subscribe (pub/sub)** — модель, в которой одно сообщение получают **все** подписчики, каждый свою копию. Служит для уведомления о факте, а не для распределения работы.

**Competing consumers** («конкурирующие потребители») — несколько воркеров, читающих одну очередь. Брокер сам решает, кому отдать очередное сообщение; координации между воркерами нет.

**Payload** — полезная нагрузка сообщения: аргументы задачи. Должен быть маленьким; большие данные кладут в хранилище, а в сообщении передают ссылку.

**Сериализация** (*serialization*) — преобразование аргументов задачи в формат передачи (JSON). В проекте разрешён только JSON: `pickle` позволяет выполнить произвольный код при доступе к брокеру и привязывает сообщения к версии классов.

## 2. Надёжность и гарантии доставки

**Подтверждение** (*ack, acknowledgement*) — сигнал воркера брокеру «сообщение обработано, можно удалять». **Nack / reject** — «не обработано»: с возвратом в очередь или без.

**At-most-once** («не более одного раза») — подтверждение отправляется сразу при получении. Задача не выполнится дважды, но может потеряться при падении воркера.

**At-least-once** («хотя бы один раз») — подтверждение отправляется после выполнения. Задача не потеряется, но может выполниться повторно.

**Exactly-once** («ровно один раз») — недостижимая в распределённой системе гарантия: между выполнением и подтверждением всегда есть момент отказа. На практике эмулируется как at-least-once + идемпотентность.

**`acks_late`** — настройка Celery, включающая подтверждение после выполнения задачи (то есть at-least-once). По умолчанию выключена.

**Идемпотентность** (*idempotence*) — свойство операции давать тот же результат при повторном выполнении с теми же входными данными. Обязательное условие при at-least-once. В проекте обеспечивается фиксированным `report_id` и `seed`: повтор перезаписывает те же файлы тем же содержимым.

**Ключ идемпотентности** — идентификатор, по которому система узнаёт повторную операцию (у нас — идентификатор отчёта, он же `task_id`).

**Visibility timeout** («таймаут видимости») — время, на которое сообщение прячется от других потребителей после выдачи. Если подтверждение не пришло, сообщение снова становится видимым. Так Redis-транспорт Celery эмулирует ack; по умолчанию — **1 час**.

**Prefetch (QoS)** — сколько сообщений потребитель может держать невыполненными одновременно. `prefetch=1` — брать по одной задаче: честное распределение между воркерами, но меньшая пропускная способность на микрозадачах.

**Retry (повтор)** — повторный запуск задачи после ошибки. В Celery — `autoretry_for`, в RQ — `Retry(max=…, interval=[…])`.

**Экспоненциальный backoff** — рост паузы между повторами (2, 4, 8, 16 секунд): даёт внешнему сервису время восстановиться.

**Jitter** («дрожание») — случайный разброс паузы перед повтором, чтобы повторы от разных воркеров не пришли одновременно и не добили сервис, который только поднялся.

**Poison message** («ядовитое сообщение») — сообщение, которое всегда приводит к ошибке. Без ограничения попыток блокирует обработку, поэтому его отправляют в dead-letter.

**Dead letter queue (DLQ) / Dead letter exchange (DLX)** — очередь (обменник) для сообщений, которые не удалось обработать за N попыток или которые были отвергнуты. Разбирает человек.

**Durable queue / persistent message** — очередь и сообщения, переживающие перезапуск брокера (за счёт записи на диск).

**Publisher confirms** — подтверждение брокером факта приёма опубликованного сообщения. В AMQP по умолчанию выключены: publish «в сокет и забыл». Включение даёт гарантию, но в эксперименте снизило скорость постановки с 2333 до 210 сообщений/с.

**Graceful shutdown (тёплая остановка)** — воркер дорабатывает текущие задачи и завершается (SIGTERM). **Cold shutdown (холодная)** — немедленное завершение с закрытием соединения и возвратом неподтверждённых задач в очередь (SIGQUIT). **SIGKILL** — процесс убит без закрытия соединения: задача вернётся только по visibility timeout или heartbeat.

**Heartbeat** — периодические служебные сообщения, по пропаже которых брокер понимает, что соединение мертво. В Celery по умолчанию 120 секунд.

## 3. Redis как брокер

**Redis** — in-memory сервер структур данных (строки, списки, множества, хеши, streams). Однопоточный по обработке команд.

**`LPUSH` / `BRPOP`** — команды работы со списком: положить в начало и блокирующе забрать с конца. На этой паре и строится очередь задач в Redis.

**Redis Streams** — тип данных, реализующий журнал сообщений с группами потребителей (`XADD`, `XREADGROUP`, `XACK`) и подтверждениями. Более «честная» очередь, чем список, но Celery по умолчанию использует списки.

**Consumer group** — группа потребителей Redis Streams или Kafka, между которыми распределяются сообщения; каждое сообщение обрабатывает один участник группы.

**PEL (Pending Entries List)** — список сообщений, выданных потребителям, но ещё не подтверждённых (Redis Streams).

**RDB / AOF** — способы персистентности Redis: периодический снимок памяти и журнал команд. При `appendfsync everysec` можно потерять до секунды записей.

**Round-trip (RTT)** — время на отправку команды и получение ответа. Каждая команда Redis синхронна: в эксперименте RTT между контейнерами ≈110 микросекунд, поэтому цена задачи определяется числом обращений, а не скоростью Redis.

**Pipeline (конвейер)** — отправка нескольких команд Redis без ожидания ответа на каждую. В замере поднимает скорость с 9 тысяч до 106 тысяч операций в секунду.

## 4. RabbitMQ и AMQP

**AMQP 0-9-1** — открытый протокол обмена сообщениями, который реализует RabbitMQ.

**Exchange (обменник)** — точка, куда публикуется сообщение. Сам сообщения не хранит: по правилам привязки раскладывает копии по очередям.

**Binding (привязка)** — правило «сообщения из обменника X с ключом Y идут в очередь Z».

**Routing key (ключ маршрутизации)** — метка сообщения, по которой обменник выбирает очереди.

**Типы обменников**: `direct` — по точному совпадению ключа; `topic` — по шаблону с `*` и `#`; `fanout` — во все привязанные очереди (pub/sub); `headers` — по заголовкам.

**Vhost (виртуальный хост)** — логически изолированное пространство очередей и обменников внутри одного брокера.

**Management UI** — веб-интерфейс RabbitMQ (порт 15672): очереди, потребители, скорость, неподтверждённые сообщения.

**Unacked** — сообщения, выданные потребителю, но ещё не подтверждённые. Растущее число unacked — признак зависших воркеров.

## 5. Kafka (для сравнения)

**Kafka** — распределённый журнал (лог) сообщений. Сообщение после чтения не исчезает: его можно перечитать.

**Партиция** (*partition*) — часть топика; порядок гарантируется только внутри партиции, а число партиций ограничивает параллелизм.

**Offset (смещение)** — позиция потребителя в логе. Потребитель подтверждает не отдельное сообщение, а позицию, поэтому «вернуть одно упавшее сообщение» нельзя — строят отдельные retry-топики.

**Replay** — повторное чтение истории сообщений с произвольной позиции. Главное преимущество Kafka и причина, по которой её берут для событий, а не для задач.

## 6. Celery

**Celery** — фреймворк фоновых задач для Python (с 2009 года), де-факто стандарт.

**Celery app** — объект приложения: конфигурация и реестр задач.

**Broker URL** — адрес транспорта (`redis://…`, `amqp://…`). Меняется переменной окружения, код задач при этом не меняется.

**Result backend** — хранилище состояний и результатов задач (в проекте — отдельный Redis). Брокер и backend — разные роли: транспорт против хранилища.

**kombu** — библиотека, абстрагирующая транспорт (RabbitMQ, Redis, SQS) для Celery.

**`delay()` / `apply_async()`** — публикация задачи. Второй вариант позволяет указать очередь, приоритет, отложенный запуск.

**`AsyncResult`** — объект для чтения состояния и результата задачи по идентификатору.

**`PENDING`** — состояние Celery, означающее «про этот идентификатор ничего не известно»: и «ещё в очереди», и «такой задачи не существует». Отличить нельзя — это особенность result backend.

**Canvas** — средства композиции задач Celery.

**Signature (подпись)** — «замороженный» вызов задачи с аргументами, который можно передавать и комбинировать.

**Chain (цепочка)** — последовательное выполнение: результат предыдущей задачи передаётся в следующую.

**Group (группа)** — параллельный запуск набора задач.

**Chord (аккорд)** — группа плюс завершающая задача, получающая список результатов группы.

**Celery beat** — планировщик периодических задач (аналог cron внутри приложения).

**Flower** — веб-мониторинг Celery: воркеры, задачи, очереди. Работает на потоке событий, который сам стоит по сообщению на каждый переход задачи.

**Пул воркера** (*pool*): `prefork` — процессы (по умолчанию, для CPU), `threads` — потоки, `gevent`/`eventlet` — кооперативная многозадачность для тысяч IO-задач, `solo` — один поток (отладка, Windows).

**`worker_max_tasks_per_child`** — перезапуск дочернего процесса каждые N задач; дешёвая защита от утечек памяти.

**Rate limit** — ограничение частоты выполнения задач (например, 10 в секунду) при работе с чужим API.

**Time limit (soft/hard)** — предельное время выполнения задачи: мягкое бросает исключение, жёсткое убивает процесс.

## 7. RQ (Redis Queue)

**RQ** — минималистичный фреймворк фоновых задач поверх Redis. Задача — обычная функция, очередь — имя плюс соединение.

**Job** — объект задачи в RQ: аргументы, статус, метаданные, результат.

**`job.meta`** — словарь произвольных данных задачи; в проекте через него передаётся прогресс.

**Статусы RQ**: `queued`, `started`, `deferred` (ждёт зависимость), `scheduled` (отложена по времени), `finished`, `failed`. В отличие от Celery, RQ умеет ответить «такой задачи нет».

**`Worker` vs `SimpleWorker`** — обычный воркер делает **fork** на каждую задачу (изоляция), Simple выполняет задачу в своём процессе (быстрее, но падение задачи роняет воркер).

**Fork** — системный вызов создания дочернего процесса копированием текущего. Нет на Windows. В замере стоит ≈72 миллисекунды на задачу.

**`depends_on`** — запуск задачи после успешного завершения другой; так в RQ собираются пайплайны.

**Failed job registry** — реестр упавших задач с трассировками, откуда их можно перезапустить.

**RQ Scheduler** — компонент, без которого не работают отложенные повторы (`with_scheduler=True` при запуске воркера).

## 8. Асинхронность в Python и альтернативы

**asyncio / event loop** — встроенная в Python кооперативная асинхронность. Синхронный вызов (например, `delay()`) блокирует цикл событий.

**`BackgroundTasks` (FastAPI)** — выполнение функции после ответа в том же процессе: без брокера, без повторов, без переживания перезапуска.

**Dramatiq / arq / Taskiq / Huey** — альтернативные очереди задач: проще Celery, часть из них — asyncio-native.

**APScheduler** — планировщик заданий (расписание), а не очередь задач.

**Temporal / Prefect** — workflow-движки: долгие бизнес-процессы с сохранением состояния, ретраями и компенсациями.

## 9. Архитектурные паттерны

**Transactional outbox** — паттерн, решающий проблему «записать в БД и поставить задачу атомарно»: задача записывается в ту же базу в той же транзакции, отдельный процесс публикует её в брокер.

**Шардирование по ключу** — маршрутизация задач одного клиента/сущности в одну очередь или к одному воркеру, чтобы сохранить порядок.

**Буферизация пиков** — использование очереди как амортизатора: при наплыве растёт очередь, а не число ошибок.

**Горизонтальное масштабирование** — увеличение производительности добавлением одинаковых процессов, без изменения кода.

**Polling (опрос)** — периодические запросы клиента о статусе (в проекте — раз в 400 мс). Альтернативы: SSE, WebSocket, webhook.

**`202 Accepted`** — HTTP-код «запрос принят в обработку»: ответ не содержит результата, только идентификатор и ссылку на статус.

**Протокол `TaskBackend`** (термин проекта) — интерфейс из двух методов (`enqueue_report`, `get_status`), через который API работает с очередью, не зная о Celery или RQ.

## 10. Метрики и эксперимент

**Пропускная способность** (*throughput*) — число задач, обработанных в секунду. В эксперименте измеряется на заранее наполненной очереди, чтобы не измерять скорость продьюсера.

**Скорость постановки** (*enqueue rate*) — сколько сообщений в секунду публикует один продьюсер последовательно.

**Задержка** (*latency*) — время от постановки задачи до её завершения. В корректном замере — на пустой очереди, иначе измеряется ожидание в очереди.

**Перцентили p50 / p95 / p99** — значения, ниже которых лежат 50 %, 95 % и 99 % измерений. p50 (медиана) описывает типичный случай, p95/p99 — «хвост», который и чувствуют пользователи.

**Накладные расходы очереди** (*overhead*) — цена прохода одной задачи через очередь без полезной работы: сериализация, передача, ack, запись результата. В проекте — 1,8 мс у Celery.

**Закон Литтла** — соотношение «среднее число заявок в системе = интенсивность × среднее время пребывания». Объясняет, почему при полной очереди «задержка» отражает позицию в очереди, а не скорость брокера.

**Медиана повторов** — способ убрать выбросы: каждая ячейка матрицы измеряется трижды, берётся среднее значение по порядку.

**Матрица эксперимента** — перебор сочетаний «конфигурация × вид задачи × число воркеров × повтор»; в проекте 135 прогонов.

**WSL2** — подсистема Linux в Windows, на которой работает Docker Desktop. Даёт заметные накладные расходы на `fork` и сетевые операции — это оговорка ко всем абсолютным цифрам эксперимента.
